## F1 — The served prompt's trace scope is module state in the caller package; a process must hold one copy of `@synadia-ai/agents`

**Measured (2026-09-16):** `AgentService` binds the served prompt's `(thread, root)` with `bindActiveTrace`, and `Agent.prompt()` reads it with `activeTrace()`; both go through one `AsyncLocalStorage` declared at module level in the caller package's `trace.ts`. The record counters next to it were moved onto `globalThis` for exactly the case of two installed copies (the SDK's own comment says so); the storage was not. A process that loads the caller package twice, once for the host package and once for the agent's own client, would write every `prompt_agent` edge with `parent_id: null`, silently: a forest of roots instead of a tree.

**Evidence:** a probe that resolves `@synadia-ai/agents` from the consumer and from the host package's entry file, binds a scope through one and reads it through the other. On this machine both resolve to one path, under `npm install` (npm symlinks `file:` packages, and bun 1.4.0's `file:` install inside `agent-sdk/typescript` is a directory of per-file symlinks into `client-sdk/typescript`, so real paths coincide) and under `npm install --install-links` (both packages copied into the consumer, no nested copy). The layout under the host package decides; `agents/ts/.npmrc` sets `install-links=true` so this repo's outcome does not depend on how the SDK checkout's own `node_modules` were made. `agents/ts/test/tools.test.ts` asserts the parentage and would catch a regression. **Added 2026-09-17:** a copy made with `install-links=true` is not refreshed by `npm install` when the SDK is rebuilt at the same version; after the move to `mario/tracing-integration` the copies under `agents/ts/node_modules/@synadia-ai/` still held the build of 2026-09-16 (`diff -r` against the checkout's `dist/`). Removing the two directories and running `npm install` again gave identical copies.

**Belongs to:** the SDK. The fix is the one already applied to the counters: hold the storage on `globalThis` under a well-known symbol, so a duplicate install still traces. Recorded in `PLAN.md` under asks; asked on 2026-09-16.

**Resolved (2026-09-19):** synadia-agents #200 holds the served prompt's `AsyncLocalStorage` on `globalThis` under a well-known symbol, as the counters were; on `sdk-release-rollout` since #201 (`fbd16ab`, 2026-09-18), which this repo consumes. `agents/ts/.npmrc` and its `install-links=true` are removed: npm installs the two `file:` links as symlinks, and on this machine both routes to `@synadia-ai/agents`, the agent's own and the host package's, resolve to the one file `client-sdk/typescript/dist/index.js`, so there is one copy anyway and the scope would survive two. `make test-ts` green after the reinstall, 41 tests, `test/tools.test.ts` asserting the child's `parent_id` among them. A rebuild of the SDK is now what the agent runs next, with nothing to reinstall here.

## F2 — bun 1.4.0 cannot install a consumer outside the SDK monorepo that links both packages by `file:`

**Measured (2026-09-16):** `bun install` in `agents/ts`, with `@synadia-ai/agents: file:../../../synadia-agents/client-sdk/typescript` and `@synadia-ai/agent-service: file:../../../synadia-agents/agent-sdk/typescript`, fails: bun resolves the host package's own dependency `file:../../client-sdk/typescript` against the consumer's directory and reports `@synadia-ai/agent-service@file:../../agent-sdk/typescript failed to resolve`. ## F3 — On a nats-server without accounts an agent's identity has `$G` as its account half, which the fabric's schemas do not admit

**Measured (2026-09-16):** the SDK's `AGENT_ID_REGEX` accepts an account public key, a config-file account name, or `$G`; the fabric's `docs/schemas/edge.json` accepts the key only (`^A[A-Z2-7]{55}\.U[A-Z2-7]{55}$`). An edge written on a plain test server, as in this repo's tests, is a valid SDK record and an invalid fabric record. No consequence on the fabric, which runs in operator mode. Consequence for tests: validating records against the fabric's schemas needs a server with account keys, such as the test repo's rig. This repo's `tools/discover_agents.result.json` uses the SDK's grammar for `identity`, because the tool hands back what the SDK reports.

**Belongs to:** the test repo, as a note for its scenarios; this repo's tests.

## F6 — Resolving a ScratchPad reference through the `sp` CLI needs the whole `ref.make` reply, not the ref record

**Measured (2026-09-16, against ScratchPad's own rig, `sp-rig` at `5400e18`):** the API's `ref.resolve` request is `{ref: <ref record>}`, but the CLI's `-ref` flag reads a saved `ref.make` reply and refuses one without `source_sequence` (`invalid_request: source_sequence is required`), the sequence it checks the projection against. A reference that travels between agents as text therefore has to carry the sequence too. Both reference agents encode the whole reply as the `sp-ref:` token (371 characters for a reply path; 333 without the sequence). With that, the round trip works: a commit in about 230 ms, a resolve and read in about 55 ms, and ScratchPad's `TRACE` shows the `sp.commit` and `sp.read` records under the thread and root ids the agent passed (`sp-afo replay`).

**Belongs to:** ScratchPad's thin clients: a handoff token format that carries what `ref.resolve` needs, so agents in different languages exchange one string.

## F7 — ScratchPad grants as a reference agent makes them: what the rig showed

**Measured (2026-09-16, the test repo's `examples` environment: ScratchPad `5400e18` on the SP account, the TypeScript agent as `T1/agent-1`, the Python agent as `T1/agent-2`, `qwen3:30b-a3b-instruct-2507` behind the proxy):**

1. **Nothing is readable without a grant, and both verbs say so the same way.** Agent-2 running `sp cat` on a path agent-1 committed, and `sp ref resolve` on agent-1's reference, are each refused with `{"error":{"code":"permission_denied","message":"permission denied","retryable":false}}` on stderr and exit 13; the console shows each as `read denied permission_denied` on agent-2's timeline (one `sp.read` record per refusal).
2. **A grant on the one path is enough.** `sp grant issue -volume-id <v> -grantee-account <A…> -grantee-user <U…> -subtree <the reference's path> -actions read -expires-at <now + 600> -operation-id <uuid>` by the volume's owner lets the grantee `ref resolve` the reference and `cat` its path at the reference's root: four `sp.read ok` records on the grantee's timeline (the resolve, and the three one `cat` writes, the test repo's F15), the content back in 60 ms. `GrantScope` admits one kind per grant — subtree, root or snapshot (`api/validate.go`, "scope must select at most one") — so the path and the root cannot be combined; the path is the tighter of the two for a volume of replies, where a grant on the root would open every earlier reply at that commit. `expires_at` is unix seconds, as on a ref.
3. **No delegation in v1, so handing on means copying.** `GrantIssueRequest.delegator_grant_id` is refused ("not supported in the v1 MVP"); only the volume's owner grants. An agent that hands a reference into another agent's volume on therefore reads it (four `sp.read ok` on the other volume, under its served thread), commits a copy into its own volume (one `sp.commit ok`) and grants the receiver read on the copy (one `sp.grant ok`); the receiver's four reads are then on the copy's volume. Measured on the assistant's thread `e5a88f20` and the helper's child thread `41e8181f`. The grant made inside `prompt_agent` carries the model's tool call id (`-tool-call-id`), and the console lists it under that tool call. **Superseded on 2026-09-17:** the copy is gone. ScratchPad's owner answered that delegation was left out of v1 on purpose, because read permission is not permission to delegate; the copy took exactly that permission. The agent now asks the creator to grant the final recipient (F13).
4. **A reply's reference is useless to the caller without a grant to the caller.** The served prompt's sender is verified (`trust: "verified"`, on the rig with the account claimed, not attested), so the agent grants that identity read on the reply's path right before sending; the caller then resolves and reads. Without this the handoff between two agents never starts: the coordinator could not read what the researcher handed back.
5. **Timings on this laptop:** a plain prompt with the commit and the grant 37 s (the model loading); a delegation with a handoff 154 to 157 s (three model calls of 25 to 50 s; every `sp` call tens of milliseconds); the reply-side commit plus grant under a second.

**Belongs to:** this repo (the handoff as `team/README.md` describes it; its rules confirmed by the fabric's owner on 2026-09-16 and recorded as a decision in `CLAUDE.md`). ScratchPad: a delegated grant, asked of its owner the same night; answered on 2026-09-17: excluded from v1 on purpose, a dedicated delegation after a refactoring, nothing more to ask (`PLAN.md` asks table, F13). The test repo's `scenarios/examples`, when it comes: the record counts above are what to assert.

## F13 — Handing on what another agent created: the creator grants at the holder's request, in code; what the rig showed

**Why:** ScratchPad's owner answered the delegated-grant ask on 2026-09-17. Delegation was left out of v1 on purpose: read permission is not permission to delegate. In the team the researcher authorizes the coordinator to read; the coordinator authorizing the writer needs permission from the original authority. A verified recipient, one path and a ten-minute expiry constrain the access; they do not establish the coordinator's right to delegate. So the copy-on-handoff of F7 item 3 sidestepped exactly that permission, and must not be what a customer copies. The replacement, decided the same day: `prompt_agent` asks the creator to grant the final recipient, code to code, never seen or decided by a model; the creator's code decides by policy; on no answer or a refusal, strip the reference and send the text; the copy removed.

**Built (branch `delegated-grant-request`, both languages):** `grant-request.ts` / `grant_request.py`, the ledger and `owns` / `granted` in the ScratchPad wrappers (`hasGranted` until the rule of item 9), the `creator` field in the `sp-ref:` token, the two schemas under `tools/`. `tools/README.md` has the exchange and the rule.

**Measured (2026-09-17, the test repo's `examples` environment, run `20260917-171800-13caa0`: the console at `67b6031`, the proxy `dev` at `e58e49a`, ScratchPad `6764a48`, the SDKs at `mario/tracing-integration` `d819fc2`; the team of five, every role on `anthropic/claude-sonnet-5` through OpenRouter; the coordinator in TypeScript, the researcher in Python):**

1. **Nothing in the SDK or ScratchPad was missing.** The TypeScript host SDK takes the endpoint as `extraEndpoints`, both caller SDKs sign a single-reply request (`requestSigned`, `request_signed`), and both host SDKs export the admission their prompt endpoint runs (`SenderGate`: header, signature over subject and payload, timestamp, nonce). The Python `AgentService` takes no extra endpoints, so the Python agent subscribes next to its service (`nc.subscribe`, queue group `agents`); an ask to the Python SDK's owner, and not a blocker: the side subscription stays. The rig's tenant users may publish and subscribe on `agents.sp-grant.>`: the request went through with the rig's credentials as issued.
2. **What tells a holder whom to ask.** ScratchPad's `Ref` and `Volume` carry no owner (`api/types.go`), so the token does: `creator`, the creating agent's prompt address, next to the `ref.make` reply (F6). It is application data like the rest of the token, so it says whom to ask and proves nothing: the requester sends only to an address discovery shows with a verified identity, on a subject it derives itself, and the creator's rule decides. The `sp` CLI gets the `ref.make` reply back without the field. A token with the field is 434 characters in this run; without it the same references were 361 to 373 (the earlier transcripts).
3. **The run.** One topic, **60.8 s** for the whole tree `38c22262`, five threads, 10 model calls, 34521 tokens in and 4452 out, every delegation on its first try (the run before it, `ef04e260`, 62.6 s, the same). In the order the console's `TRACE` sequence gives: `seq 42` the coordinator's third model call, which asks for `prompt_agent` on the writer with the researcher's reference; **`seq 43` `sp.grant ok` by the researcher, on the coordinator's thread `38c22262`, under the coordinator's tool call `toolu_01C3pGxU…`**; `seq 44` the coordinator's edge to the writer's thread `f1537817`; `seq 45` to `48` the writer's four `sp.read ok` **on the researcher's volume `gfFJ68NC`**; `seq 49` the writer's model call; then its own commit and grant. Between `seq 42` and `seq 44` the coordinator has no ScratchPad record of its own: no read, no commit of a copy, no grant. The researcher's log: `[sp-grant] granted <writer> read on sp-ref:… at the request of <coordinator>`. The writer's: `read sp-ref:… (1076 chars)`.
4. **The raw record** of the first run's grant (`TRACE` sequence 14, a direct get as the console's reader): `kind: sp.grant`, `agent` the researcher, `decision: ok`, `grant.action: issue`, `grant.grantee` the writer, `grant.scope.subtree: /replies/5975527a….md` (the researcher's reply, the one path), `grant.actions: ["read"]`, `grant.expires` the record's `ts` plus 600, `thread_id` and `root_id` the coordinator's `ef04e260…`, `tool_call_id` the coordinator's call to the writer.
5. **The console shows a record one agent made on another agent's thread.** ScratchPad copies the trace fields and authenticates on none (AFO design §6.3), and the console files the record by them: the researcher's grant is an item of the coordinator's root thread, its `agent` the researcher, its `tool_call_id` the coordinator's, in `thread.get`, and the last item of the researcher's timeline with the coordinator's thread on it. `team/transcript.py` now names who made each ScratchPad record, and renders this one under the tool call: "grant ×1 by **researcher**" (`docs/runs/2026-09-17-7-team-of-five-grant-request.md`).
6. **The rule refuses, on the rig's real identities.** The caller, signed and never granted the researcher's reference, asked the researcher to grant the writer: `{"granted": false, "reason": "this agent holds no live read grant it made to the requester on that reference"}`, and the researcher's log says the same. The same request to PI's address: `no responders: 'agents.sp-grant.pi.team.editor'`, at once; a harness has no such endpoint, and needs none while it reads no references. The requester was TypeScript and the creator Python, so the two implementations agree on the wire. The remaining lines of the rule (no signature, a replayed request, a request for oneself, another volume's reference, a body that is no request) are in both test suites on a real `nats-server`, not repeated on the rig.
7. **`owns` must not create a volume.** In the first run the coordinator's timeline had a `commit ok` between its model call and the writer's edge: its volume being created, because asking "is this reference in my volume?" went through the call that creates the volume when there is none. An agent that has committed nothing owns nothing: `owns` now lists and never creates, and the second run shows the coordinator's volume created with its reply, where it belongs.
8. **Every tree shows once.** With the thread record's new shape (the fabric's rule that a thread record carries `thread_id` and `root_id` bare, and the harness pair only for a harness's own thread) on the proxy, the console and the plugins, `threads.list` has one row per prompt, with the tree's usage on it (10 calls, 34521 / 4452), and OpenClaw's and PI's calls in the same tree. The `sdk:` twin of the test repo's F2, which every earlier entry here and in the plan's log describes, is gone; `team/transcript.py` keeps the merge only for console answers saved before 2026-09-17.

9. **Reversed by the fabric's owner on 2026-09-17: a grant made on request confers no right to ask.** As first built, the agent granted at someone's request was in the ledger like any other grantee, so it could ask in turn, and that agent's grantee again: access relayed from agent to agent, each hop one the creator never chose. That is ScratchPad's owner's exact concern, and what a customer copies must be conservative. Now only an agent the creator granted **first-hand** may ask: the verified caller of its reply, or the recipient of a reference it handed over itself. The ledger keeps the two kinds apart (`GrantKind`, `granted()` answering `first-hand`, `on-request` or nothing; a first-hand grant still running is not hidden by a later one made on request), because ScratchPad knows the grants and not how they came about. A refusal of its own words: "the requester's own grant was made at another agent's request; only an agent this agent handed the reference itself may ask for another". In both test suites the third agent, granted on request, asks for a fourth and for the requester, is refused both times, and nothing is granted or recorded. **The team rerun once to show nothing else changed** (run `20260917-200048-0425c5`, the same commits of console, proxy and ScratchPad; Sonnet 5 through OpenRouter): **57.7 s**, tree `d6eb4bf4`, five threads, 10 model calls, 33843 tokens in and 3997 out, every delegation on its first try, and the same sequence: `seq 12` the coordinator's model call, `seq 13` `sp.grant ok` by the researcher on the coordinator's thread under its tool call, `seq 15` to `18` the writer's four reads on the researcher's volume, nothing of the coordinator's in between, no refusal in any log. Then, with the rig's identities and the grants still live: the writer, granted on request, asked the researcher to grant the caller and was refused in those words; the coordinator, granted first-hand, asked the same and was granted. TypeScript asking Python both times.
10. **The rerun's rig was a private copy, because the console's checkout was mid-change.** `aft env up` refused: `../agent-fabric-console` was on `mario/presence` with modified provisioning sources and new files, the console session's work on the receive-only agent (F14 item 2). The waivers (`-any-branch -allow-dirty`) would have built `provision` and the console from that unfinished tree, and a rerun meant to show that nothing else changed would have run on a fabric that did. Earlier sessions used the waivers only when the console's changes were documents. So the rig was stood up from a copy under this repo's gitignored `local/rigs/`: clones of the test repo (`master`, `338e122`), the console (`master`, `67b6031`), the proxy (`dev`, `e58e49a`) and ScratchPad (`main`, `6764a48`), each at its sibling's commit, the fabric docs and the agents checkout linked; no waiver, 25 checks passed, no sibling's tree touched. Linking the proxy does not work: the test repo's F14 bridge injects a test file by absolute path (`go test -overlay`), and through a symlink Go resolves the package to its real path and finds "no tests to run"; a clone does.

**Limits, stated:** the ledger is in memory and per process, so after a restart, or in a second instance behind the same address (the endpoint is in the `agents` queue group), a request is refused and the text goes without the reference, which is the safe failure. ScratchPad's `grant list` is the durable record, but it lists every grant a volume ever had (`internal/service/metadata.go`), so its cost grows with the volume's history. Since item 9, access cannot be renewed in turns: an agent granted on request cannot ask, a first-hand grantee cannot ask for itself, so nobody's access outlasts the creator's last first-hand grant by more than one expiry. The expiry is still hygiene, not a wall against an agent that already read the content. The strip-and-send path (creator gone, or refusing) did not fire on the rig; it is in both tool tests.

**Rules, and the fabric's owner's word on them (2026-09-17). Confirmed:** the creator's address in the token; the subject `agents.sp-grant.<agent>.<owner>.<name>`, derived by the requester and never taken from the token or from metadata; a *live* grant as the entitlement; a request for oneself refused. **Reversed:** the agent granted at someone's request may *not* ask in turn (item 9). **Taken and not yet spoken to:** no new metadata key (no responders is the answer of an agent without the endpoint); the requester's thread and tool call as labels on the creator's grant; ten seconds for the answer; a failed grant on the agent's *own* content still stops the prompt, as before.

**Belongs to:** this repo (`tools/README.md`, `team/README.md`, `CLAUDE.md`'s decision). ScratchPad: nothing to ask; when its delegation exists, the creator's rule becomes a delegable grant and the exchange goes. The Python SDK: `extra_endpoints` on the Python `AgentService`, as TypeScript has (`PLAN.md` asks table; not blocking). The test repo: its `TestAGranteeCannotPassItsGrantOn` (its PR #19) asserts the ScratchPad half of the same rule.
## F14 — Following the getting-started pages on the rig: three things a first reader would have hit

## F29 — An empty completion while a call waits on a question ended the turn as done, with an empty reply

**Observed 2026-09-27 on a live stack.** The coordinator's model delegated, the prompted agent asked three permission questions in turn, and the model answered each with `answer_agent`. After the fourth question the model returned a completion with `content: null` and no tool calls. `converse` took that as the final reply: the turn ended `ok`, the caller got an empty reply, and the call that was waiting on the fourth question ended with the served prompt.

**Fixed in both agents** (`src/model.ts`, `fabric_agent/model.py`). `converse` follows the calls the model started through the tools' own results, each of which carries the call's `call_id` and `state` and, while it is `input_required`, the question. An empty completion while any call is `input_required` or `running` is not a reply:
- the empty answer is dropped from the conversation;
- the model is told which calls wait and on what (the call, whom it went to, the question, `answer_agent`), and is asked again;
- after two such re-asks a third empty completion fails the turn with `EmptyReplyError`, which the agent raises as a `RequestRejectedError(500, …)`. The caller sees `the model returned an empty reply 3 times while 1 call it started was still open (…); no reply was produced`, never `ok` with nothing.

An empty completion with no call open is still the reply, as before. The tests: `typescript/test/model.test.ts` and `python/tests/test_model.py` drive `converse` with a scripted model; the agent tests' fake model has two new modes, `hush` (empty once, then `answer_agent` when told) and `mute` (empty every time), against the agent that asks before it answers.

**Where it belongs.** The agents track the calls from the tool results because `AgentTools` exposes no list of a served prompt's open calls outside `execute()` (`list_agent_calls` is offered only with the six tools). Every model loop built on `AgentTools` has the same end-of-turn question, so a public accessor on `AgentTools` in the protocol SDK, the served scope's open calls with their state and pending question, would let each loop ask it instead of parsing results. Proposed, not done.
